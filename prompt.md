# 1. ДЕФОЛТНЫЙ СТЕК (всё в бесплатных лимитах)

Меняй только при явной причине и с объяснением.

## Бот
- **TypeScript + grammY**, режим **webhook** (не long polling — см. §3.2).
- Плагины: `@grammyjs/auto-retry` (429/retry_after),
  `@grammyjs/transformer-throttler` (лимиты API),
  `@grammyjs/conversations` (многошаговые диалоги),
  `@grammyjs/menu` (инлайн-меню), `@grammyjs/i18n` (RU/EN),
  `@grammyjs/ratelimiter` (антифлуд).
- Валидация входных данных — **zod** на всех границах.

## Хостинг и данные — Cloudflare (одна платформа, одна консоль, один деплой)
| Задача | Сервис | Бесплатный лимит | Что при превышении |
|---|---|---|---|
| Рантайм бота | Workers | 100k req/сутки, 10 ms CPU/запрос | 429 от CF → апгрейд или вынос тяжёлого в cron |
| БД | D1 (SQLite) | ~5 GB, лимиты на чтения/записи в сутки | миграция на Turso / Neon free |
| Кэш, флаги, дедуп update_id | KV | ~100k чтений, **~1k записей/сутки** | записей мало — сессии в KV НЕ храни, только в D1 |
| Файлы | R2 | 10 GB | либо использовать Telegram как CDN (`file_id`) |
| Фронт Mini App | Pages | статика без лимита запросов | — |
| Крон-задачи | Cron Triggers | входит в Workers | GitHub Actions schedule |

**Явное предупреждение по CPU-лимиту Workers free:** 10 ms CPU на запрос.
Ожидание сети (вызовы Bot API, D1) в это время не входит, но
криптография, парсинг больших JSON и циклы — входят. Всё тяжёлое —
в Cron Trigger + таблица заданий в D1.

**Альтернативы, если Cloudflare не подходит** (назови вслух причину смены):
- **Deno Deploy + Deno KV** — проще, grammY отлично живёт, щедрый free.
- **Vercel Functions + Neon/Supabase free** — если фронт уже на Next.js.
- ❌ Render/Railway free — холодный старт убивает UX вебхука.
- ❌ Long polling на любом free-инстансе, который засыпает.

## Mini App (фронтенд)
- **React + Vite + TypeScript** — дефолт: мгновенный билд, статика на Pages,
  ноль серверного рантайма (= ноль расходов).
- `@telegram-apps/sdk-react` — типизированный доступ к WebApp API.
- `@telegram-apps/telegram-ui` — нативный внешний вид Telegram из коробки.
- Состояние: TanStack Query. Никакого Redux в MVP.
- **Меняй фронт-стек, если:** нужен SEO/SSR или публичная веб-версия → Next.js
  на Vercel free; проект — игра/канвас → Vite + чистый TS без UI-кита;
  команда уже на Vue/Svelte → бери привычное, ORM-совместимость не пострадает.

## Монорепозиторий
~~~
apps/
  bot/        # grammY на Workers, wrangler.toml
  miniapp/    # Vite + React, деплой на Pages
packages/
  shared/     # zod-схемы контрактов API + общие типы (единственный источник правды)
  db/         # drizzle-схема + миграции D1
~~~
pnpm workspaces. Drizzle ORM: `drizzle-kit generate` → `wrangler d1 migrations apply`.
Контракты бот↔Mini App описываются в `packages/shared` один раз и импортируются
обеими сторонами. Ручное дублирование типов — ошибка ревью.

# 3. ЗНАНИЯ ПЛАТФОРМЫ (правила без исключений)

## 3.1 BotFather
Чек-лист перед запуском: `/newbot` → токен; `/setdescription` (экран до
старта); `/setabouttext`; аватар; `/setcommands` (плюс `setMyCommands` со
скоупами в коде); `/setprivacy` — обязательно осознанно, если бот работает
в группах; `/newapp` для direct-link Mini App (`t.me/<bot>/<app>`);
`setChatMenuButton` для кнопки меню; `/setdomain` — только если используется
Login Widget. **Отдельный бот и отдельный токен для staging.**

## 3.2 Апдейты и вебхуки
- `setWebhook` всегда с `secret_token`; на входе сверяй заголовок
  `X-Telegram-Bot-Api-Secret-Token` **строкой постоянного времени**.
  Не совпало — `401`, без тела.
- Всегда указывай `allowed_updates` явно. Дефолт молча не доставляет
  часть типов апдейтов.
- Отвечай `200` быстро. Любой не-2xx → Telegram ретраит → **дубликаты**.
  Отсюда: дедуп по `update_id` в KV с TTL ~24 ч перед обработкой.
- На serverless дожидайся завершения обработчика до возврата ответа,
  иначе воркер умрёт на середине. Долгое — в очередь заданий в D1 + cron.
- Локальная разработка: `cloudflared tunnel --url http://localhost:8787`
  (без аккаунта) или ngrok. В dev допустим polling, в проде — нет.

## 3.3 grammY
- `bot.catch` обязателен: разделяй `GrammyError` (Telegram вернул ошибку),
  `HttpError` (сеть) и прочее. Пользователю — понятный текст, в лог —
  `update_id` и стек.
- Порядок мидлварей: dedupe → auth/бан → throttler → i18n → session →
  роутер. `sequentialize` по `chat.id`, если важен порядок сообщений.
- `@grammyjs/conversations` **реплеит** функцию диалога. Любой сайд-эффект
  (запись в БД, HTTP, `Math.random`, `Date.now`) оборачивай в
  `conversation.external()`. Это причина №1 «призрачных» багов.
- **Сессии в памяти на serverless не существуют.** Только сторедж-адаптер.
  На Cloudflare — D1, а не KV (у KV free жёсткий лимит записей в сутки).
- Всегда вызывай `answerCallbackQuery` — иначе у пользователя вечный спиннер.
- Лимиты Bot API: ~30 сообщений/сек суммарно, ~1/сек в один чат,
  ~20/мин в группу. Рассылки — только через очередь с троттлингом,
  никогда циклом `for`.
- Текст: 4096 символов на сообщение, подпись к медиа короче. Режь заранее.
- Parse mode: **`HTML` по умолчанию**. MarkdownV2 требует экранирования
  18 символов и регулярно роняет отправку на пользовательском вводе.
  Пользовательские строки экранируй всегда.

## 3.4 Mini App и initData — безопасность
**`initDataUnsafe` — это данные от клиента. Доверять нельзя никогда.**

Схема аутентификации:
1. Фронт шлёт на бэкенд заголовок `Authorization: tma <initDataRaw>`.
2. Бэкенд валидирует:
   - `data_check_string` = все пары `key=value` кроме `hash`,
     отсортированные по ключу, склеенные через `\n`;
   - `secret_key = HMAC_SHA256(key="WebAppData", data=<BOT_TOKEN>)`;
   - сверить `hex(HMAC_SHA256(data_check_string, secret_key))` с `hash`
     сравнением постоянного времени;
   - проверить свежесть `auth_date` (окно ≤ 1 часа для платёжных действий,
     ≤ 24 ч для чтения) — иначе replay.
3. `user.id` берётся **только** из провалидированных данных. Любой `userId`
   из тела запроса — игнорировать.
4. Если валидация делается сторонним сервисом без доступа к токену —
   использовать Ed25519-подпись (`signature`) вместо HMAC.

UX-правила Mini App:
- `ready()` сразу после монтирования, иначе висит лоадер Telegram.
- `expand()` — если контент выше сгиба.
- Цвета — **только** из `themeParams`. Захардкоженный белый фон = слепой
  пользователь в тёмной теме.
- Учитывай safe area insets и `viewportStableHeight` (клавиатура и панель
  Telegram меняют высоту — `100vh` врёт).
- MainButton вместо своей кнопки submit; BackButton вместо своей «назад».
- Haptic feedback на подтверждающих действиях.
- `disableVerticalSwipes()`, если свайп-закрытие конфликтует со скроллом.
- `CloudStorage` — для лёгких пользовательских настроек, не для бизнес-данных.
- Deep links: `?start=<payload>` для чата, `?startapp=<payload>` для
  Mini App → приходит в `start_param`. Основа рефералок и шаринга.
- Фичи новых версий Bot API оборачивай в `isVersionAtLeast()` + фолбэк:
  у части пользователей старые клиенты.
- Mini App требует HTTPS-домен. `localhost` не откроется — только туннель.

## 3.5 Telegram Stars (XTR) — платёжный плейбук
- `createInvoiceLink` / `sendInvoice`: `currency: "XTR"`,
  `provider_token` **пустой/отсутствует** (для Stars провайдер не нужен),
  `prices: [{ label, amount }]`, где `amount` — **целое число звёзд**.
  Не умножай на 100 — это правило фиатных валют, не XTR.
- Ограничения полей: `title` ≤ 32 симв., `description` ≤ 255,
  `payload` ≤ 128 байт. В `payload` клади **свой** идентификатор заказа,
  а не user_id — по нему потом сверяешь выдачу.
- Заказ создавай в БД **до** показа инвойса, в статусе `pending`.
- `pre_checkout_query`: ответить **обязательно в течение 10 секунд**.
  Здесь — последняя проверка (товар доступен, цена та же, лимит не превышен).
  Отказ — с человеческим текстом причины, он показывается пользователю.
- `message.successful_payment`: сохрани `telegram_payment_charge_id`
  **с уникальным индексом**. Выдача товара — в той же транзакции.
  Апдейт может прийти повторно: повторная выдача — баг, а не «страховка».
- Рефанд: `refundStarPayment(user_id, telegram_payment_charge_id)`.
  Заложи ручку/команду для владельца сразу — Telegram ожидает от вас
  адекватной работы с возвратами.
- Подписки: `createInvoiceLink` с `subscription_period` (поддерживается
  только 30-дневный период); в `successful_payment` смотри флаги
  повторного платежа; отмена/продление — через соответствующий метод
  управления подпиской. Для MVP сначала разовые покупки, подписка — вторым шагом.
- Из Mini App инвойс открывается через `openInvoice` — обработай все статусы:
  `paid`, `cancelled`, `failed`, `pending`. `pending` — не считать оплатой,
  ждать `successful_payment` на бэкенде.
- **Правовое:** за Stars продаются только цифровые товары и услуги.
  Физические товары — только через обычных платёжных провайдеров.
- Вывод средств — через Fragment после периода удержания (≈21 день).
  Предупреди владельца заранее: деньги приходят не мгновенно.
- `getStarTransactions` — для сверки баланса и расследования спорных случаев.

# 4. КОД-СТАНДАРТЫ

- TypeScript `strict: true`. `any` запрещён, `unknown` + сужение — да.
- Никаких «магических» строк: команды, callback_data, ключи i18n — константы
  в `packages/shared`.
- `callback_data` ≤ 64 байт. Схема — короткий префикс + id, не JSON.
- Все внешние данные (initData, тело запроса, callback_data, ответы API)
  проходят через zod.
- Слои: `handlers/` (только оркестрация) → `services/` (бизнес-логика,
  тестируемая без Telegram) → `repos/` (drizzle). Бизнес-логика внутри
  хендлера — отказ на ревью.
- Тексты пользователю — только через i18n, даже если язык один.
- Никаких `console.log` в проде: структурированный логгер, JSON, без PII,
  всегда с `update_id` / `request_id`.
- Идемпотентность по умолчанию: любой обработчик должен переживать
  повторную доставку того же апдейта.
- Комментарии объясняют «почему», а не «что». Особенно вокруг обходов
  ограничений Telegram — иначе через месяц их «оптимизируют» обратно.

# 5. ЧЕК-ЛИСТ БЕЗОПАСНОСТИ (гейт фазы 6)

- [ ] `BOT_TOKEN` только в серверных секретах. Проверено: он не встречается
      ни в одной `VITE_*`-переменной и ни в одном бандле фронта.
- [ ] Вебхук закрыт `secret_token`, сравнение постоянного времени.
- [ ] `initData` валидируется на каждом запросе к бэкенду; `auth_date` свежий.
- [ ] Идентичность пользователя берётся только из подписанных данных.
- [ ] Авторизация ресурсов: пользователь A не может прочитать объект пользователя B
      по прямому id (проверь руками, подставив чужой id).
- [ ] CORS — только домен Mini App. Не `*`.
- [ ] Rate limiting: на пользователя и глобальный.
- [ ] Все входы провалидированы zod; SQL только параметризованный.
- [ ] Ошибки наружу — без стеков и внутренних идентификаторов.
- [ ] Логи и аналитика без персональных данных, минимизация хранимого.
- [ ] `/delete_my_data` реализован; политика приватности и срок хранения
      описаны в `/start` или в описании бота.
- [ ] Админ-команды проверяют id по allow-list из env, а не по username.
- [ ] Двойная трата исключена: уникальный индекс на `telegram_payment_charge_id`.

# 6. ТЕСТЫ И QA

- Юнит-тесты — на `services/` без Telegram.
- Интеграционные — `bot.handleUpdate(fixture)` с перехватом исходящих
  вызовов через трансформер; фикстуры реальных апдейтов держи в `__fixtures__`.
- Обязательные тесты: валидация `initData` (валидный / протухший /
  подделанный hash), дедуп `update_id`, идемпотентность `successful_payment`,
  отказ в `pre_checkout_query`.
- Mini App — Playwright с моком Telegram WebApp.
- Ручная матрица перед релизом: iOS, Android, Desktop × тёмная/светлая тема.
  Плюс: узкий экран, медленная сеть, пользователь без username,
  пользователь заблокировал бота, повторный `/start`.
- Тестовое окружение Telegram (test DC) — для платёжных сценариев без
  реальных списаний.

# 7. DEPLOY / CI

- GitHub Actions: lint → typecheck → test → миграции D1 → `wrangler deploy`
  → сборка и деплой Pages. Прод — только по тегу или по `main`.
- Секреты: `wrangler secret put`, никогда не в `wrangler.toml`.
- Миграции всегда обратно совместимы на один релиз вперёд (сначала добавь
  колонку, потом переключи код, потом удаляй старое).
- После деплоя — автоматический `setWebhook` с актуальным URL и секретом,
  затем `getWebhookInfo` в лог: `pending_update_count` и `last_error_message`
  показывают реальное состояние.
- Откат: предыдущая версия воркера + `git revert`. Проверь, что откат кода
  не ломает уже применённую миграцию.
