## ADR-001. Источник данных: Aviasales **Data API**, а не Search API

**Статус:** принято · **Влияние:** определяющее для продукта

### Контекст

У Travelpayouts два разных API:

| | Data API | Flight Search API |
| --- | --- | --- |
| Данные | кэш, 2–7 дней | реальное время |
| Порог доступа | нет, достаточно токена | **от 50 000 MAU** |
| Стоимость | бесплатно | бесплатно, но недоступно новому проекту |

### Решение

MVP строится **только** на Data API. Real-time поиск отложен до достижения
порога MAU.

### Последствия — читать обязательно

1. **Мы показываем не текущую цену, а последнюю известную.** Это не баг,
   а свойство источника. Каждая цена приходит с полем `expires_at`.
2. **UI обязан быть честным.** Рядом с ценой всегда: «найдено N дней назад,
   актуальную цену проверим на Aviasales». Скрывать это — путь к жалобам.
3. **Мы не бронируем и не продаём билеты.** Кнопка ведёт на Aviasales по
   партнёрской ссылке с нашим `marker`. Это же и второй источник дохода.
4. **Продукт смещается от «поиска» к «идее».** Кэш плохо отвечает на
   «найди билет на завтра в 19:40», но отлично отвечает на
   «куда улететь из Москвы в марте до 20 000 ₽». Позиционирование Voolo —
   **выбор направления**, а не бронирование. Это совпадает с исходной задачей.
5. Апгрейд на Search API = замена одного модуля `providers/`, контракты
   `packages/shared` не меняются. Заложено с первого дня.

### Используемые эндпоинты

| Назначение | Эндпоинт |
| --- | --- |
| Дешёвые билеты по маршруту | `GET /v1/prices/cheap` |
| Только прямые рейсы | `GET /v1/prices/direct` |
| Цена на каждый день месяца | `GET /v1/prices/calendar` |
| Цены по месяцам | `GET /v1/prices/monthly` |
| Популярные направления из города | `GET /v1/city-directions` |
| Лучшие находки за период | `GET /v2/prices/latest` |
| Матрица цен по месяцу | `GET /v2/prices/month-matrix` |
| Соседние аэропорты и даты | `GET /v2/prices/nearest-places-matrix` |
| Спецпредложения авиакомпаний | `GET /v2/prices/special-offers` |

База: `https://api.travelpayouts.com`. Авторизация — партнёрский токен.
Валюта по умолчанию RUB, задаётся параметром `currency`.

## ADR-002. Инфраструктура: Cloudflare целиком

**Статус:** принято · **изменено 6 августа 2026** (KV убран, см. поправку)

### Решение

Workers (рантайм) + D1 (БД и всё состояние) + Cache API (кэш ответов
провайдера) + Pages (Mini App) + Cron Triggers.

### Почему

Единственная связка, где рантайм, БД, статика и крон бесплатны
**одновременно и не засыпают**. Render и Railway на free-тарифе усыпляют
инстанс — холодный старт ломает вебхук и UX Mini App.

### Поправка: почему KV убран полностью

Изначально KV брался под сессии, дедупликацию апдейтов и кэш провайдера.
Арифметика free-тарифа это убивает:

| Хранилище | Записей в сутки |
| --- | --- |
| KV | **~1 000** |
| D1 | **~100 000 строк** |

Дедуп требует одной записи на **каждый** апдейт. На KV это потолок в 1 000
апдейтов в сутки — порядка 30–50 активных пользователей. Причём лимит
выбивается тихо: бот начинает обрабатывать повторы, а дубль обработки
платежа недопустим.

Что стало вместо:

- **Сессии** — таблица `sessions` в D1 через собственный сторедж-адаптер.
- **Дедуп апдейтов** — таблица `processed_updates`, см. ADR-003.
- **Кэш ответов Travelpayouts** — `caches.default` (Cache API). Он бесплатен,
  живёт на границе и идеально подходит: данные и так кэшированные,
  терять их не страшно.

Правило на будущее: **в проекте нет KV-биндингов**. Если кажется, что нужен
ключ-значение — это или строка в D1, или запись в Cache API.

### Чем платим

| Лимит | Значение | Что делаем при приближении |
| --- | --- | --- |
| Запросы Workers | ~100k/сутки | ~3000 DAU при 30 действиях; дальше платный план |
| **CPU на запрос** | **~10 мс** | ожидание сети не считается; тяжёлое — в Cron |
| Записи D1 | ~100k строк/сутки | чистка старых строк кроном |
| Объём D1 | ~5 ГБ | запас на годы для нашей модели данных |

## ADR-003. Бот: grammY на вебхуке

**Статус:** принято · **изменено 6 августа 2026** (дедуп переехал в D1)

Long polling несовместим с serverless. Вебхук обязателен, отсюда:

- `setWebhook` всегда с `secret_token`, проверка заголовка сравнением
  постоянного времени;
- `allowed_updates` перечисляем явно;
- **дедуп по `update_id`** — таблица `processed_updates` в D1. Захват делается
  одним `INSERT ... ON CONFLICT DO NOTHING`: если строка не вставилась — апдейт
  уже обработан, возвращаем 200 и выходим. Телеграм ретраит любой не-2xx,
  а дубль обработки платежа недопустим;
- старые строки дедупа удаляет суточный крон (`pruneStaleRows`), иначе таблица
  растёт бесконечно;
- сессии — в D1 через сторедж-адаптер, не в памяти воркера.

## ADR-004. Rich Messages (Bot API 10.2) через собственный клиент

**Статус:** принято

### Контекст

Bot API 10.1 (11 июня 2026) добавил `sendRichMessage`, 10.2 (14 июля 2026) —
блочные сущности: таблицы, заголовки, списки с чекбоксами, `details`,
коллажи, слайдшоу, сноски. Лимит — 32 768 UTF-8 символов.

Для Voolo это не украшение: выдача билетов **таблична по своей природе**.
До 10.1 её приходилось верстать моноширинным текстом, который ломается на
узких экранах.

### Решение

Собственный типизированный клиент `apps/bot/src/rich/` вместо ожидания
поддержки в SDK:

1. Типы блоков описаны у нас и помечены как проверенные по документации.
2. Вызов идёт напрямую в Bot API — не зависим от версии типов grammY.
3. **Обязательный фолбэк**: при ошибке метода сообщение деградирует в
   `sendMessage` с `parse_mode: HTML` (таблица → `<pre>`, `details` →
   `<blockquote expandable>`). Пользователь на старом клиенте получает
   читаемый ответ, а не пустоту.

## ADR-005. Монетизация: Stars + партнёрская комиссия

**Статус:** принято

Два независимых потока:

1. **Telegram Stars (XTR)** — премиум-доступ внутри продукта.
2. **Партнёрские отчисления Aviasales** — с каждого перехода по ссылке.

Второй поток работает и для бесплатных пользователей, поэтому бесплатный
тариф не должен быть бесполезным: он обязан доводить до клика.

Правила Stars, зафиксированные в коде:

- `currency: "XTR"`, `provider_token` пустой, сумма — целое число звёзд
  (не умножать на 100);
- заказ создаётся в БД **до** показа инвойса;
- `pre_checkout_query` подтверждается **в течение 10 секунд**;
- `telegram_payment_charge_id` — с уникальным индексом; повторная выдача
  при повторном апдейте невозможна;
- рефанд через `refundStarPayment` доступен админу с первого релиза;
- за Stars продаются только цифровые услуги — наш случай подходит;
- вывод средств через Fragment после периода удержания (~21 день).

## ADR-006. Mini App: фирменная тёмная тема вместо `themeParams`

**Статус:** принято · **осознанное отклонение от общей рекомендации**

### Контекст

Обычная рекомендация — брать цвета из `themeParams` Telegram. Но Voolo имеет
заданную айдентику: кислотный лайм на почти чёрном.

### Решение

Фиксированная фирменная тёмная тема, как у Spotify или Netflix внутри их
приложений. При этом:

- `setHeaderColor` и `setBackgroundColor` синхронизируются с фоном бренда,
  чтобы не было шва между шапкой Telegram и приложением;
- safe area insets, `viewportStableHeight`, BackButton, MainButton и
  haptic feedback используются штатно — отклонение касается **только** палитры;
- светлая тема не поддерживается намеренно: лайм на белом теряет контраст.

### Чем платим

Пользователи светлой темы получат тёмное приложение. Для travel-контента с
фотографиями направлений это скорее плюс.

## ADR-007. Границы MVP

**Статус:** принято

### В MVP входит

- Поиск дешёвых билетов по маршруту и по гибким датам
- Подбор направления: «куда улететь из X с бюджетом Y»
- Календарь цен на месяц
- Избранные маршруты и алерт о падении цены (крон раз в сутки)
- Премиум за Stars
- Партнёрские ссылки на Aviasales
- RU + EN

### Осознанно отрезано до первых пользователей

Отели · бронирование внутри бота · мультигород · подбор по визам ·
соцфичи и шаринг подборок · реферальная программа · веб-версия вне Telegram ·
админка (первое время — SQL и команды) · A/B-тесты · пуш-рассылки по сегментам

Причина едина: ни одна из этих функций не проверяет главную гипотезу —
**готов ли пользователь платить звёздами за подсказку, куда и когда лететь дешевле**.

## ADR-008. Авторизация Mini App: подпись initData с двумя окнами жизни

**Статус:** принято

### Решение

Каждый запрос Mini App несёт заголовок `Authorization: tma <initDataRaw>`.
Сервер проверяет подпись: `secret_key = HMAC_SHA256("WebAppData", BOT_TOKEN)`,
затем сверка `hash` с `data_check_string`.

Два неочевидных момента, которые стоили бы нам часов отладки:

1. Из `data_check_string` исключаются **два** поля: `hash` и `signature`.
   Второе появилось позже и ломает проверку у тех, кто читал старые гайды.
2. Сравнение хешей — только постоянным временем.

### Два окна жизни подписи

| Операции | `auth_date` не старше | Почему |
| --- | --- | --- |
| Чтение и обычные записи | 24 ч | приложение часто висит открытым в фоне |
| `POST /api/invoice` | **1 ч** | создание платёжной ссылки — деньги |

Допускается рассинхрон часов на 300 секунд в будущее: часы клиента регулярно
спешат, и без допуска часть пользователей получит 401 на ровном месте.

### Следствия

- `userId` берётся **только** из проверенной подписи, никогда из тела запроса.
- CORS открыт на `*` осознанно: авторизация живёт в заголовке, а не в куках,
  поэтому CSRF невозможен, а домен Pages меняется от превью к превью.
- Квоты и лимиты отдаются кодами `quota_exceeded` и `watch_limit` со статусом
  **402**, чтобы клиент показал пейвол, а не красную ошибку.
